# 初始化与拆解项目工作流

## 核心原则

为现有 Windows 项目建立 Claude Code 与 Codex 共用的项目工作流，并在已有工作流的项目中按代码框架拆分项目 Skill。`.claude` 是唯一项目知识源；根目录 `AGENTS.md` 只作为 Codex 的薄入口。

初次运行只允许生成两个文件：

- `.claude/CLAUDE.md`
- `AGENTS.md`

不要创建业务 Skill、构建系统、同步工具、锁文件或其他脚手架。

## 选择工作模式

- 用户要求“初始化项目工作流”“建立项目脚手架”，且项目尚无共同工作流时，进入“初始化模式”。
- 用户说“拆解项目”“分析项目”“梳理代码框架”或“拆分项目 Skill”时自动触发本 Skill：
  - 项目没有 `.claude/CLAUDE.md` 和 `AGENTS.md` 时，先进入“初始化模式”；
  - 项目已有完整共同工作流时，进入“拆解模式”；
  - 两个入口只存在一个时停止并报告，不自动补全、覆盖或迁移。
- 无法唯一判断模式时，只问一个问题确认，不要同时执行两个模式。

## 初始化模式

### 1. 确认环境和项目根目录

- 只在 Windows 上执行。
- 用户指定目录时使用该目录；否则使用当前工作区根目录。
- 无法唯一确定项目根目录时停止并询问，不要猜测。

### 2. 先检查冲突

在读取大量项目内容之前，检查以下目标是否存在：

- `<project>/.claude/CLAUDE.md`
- `<project>/AGENTS.md`

任一目标存在时立即停止，报告准确路径。不要覆盖、合并、重命名、删除或创建备份。

### 3. 只读了解项目

只读取起草工作流所需的高价值信息：

- README 和现有项目文档；
- 项目清单、引擎或工具配置；
- 构建脚本和测试入口；
- 主要代码目录及顶层代码框架；
- 已存在的团队规则。

跳过依赖、缓存、构建产物和大型生成目录。不要运行构建、测试、格式化、安装或项目程序。

把信息分成“已由文件证实”和“需要负责人确认”两类。不得把推测写成项目事实。

### 4. 逐项询问未知信息

一次只问一个会影响工作流的问题。至少确认：

- 项目用途和主要技术环境；
- 开发、构建和验证命令；
- 方案审核与实施边界；
- 禁止修改区域和项目红线；
- 主要代码框架的名称和路径。

负责人选择暂不定义时，明确记录“尚未定义”，不要自行补全。

### 5. 起草共同工作流

`.claude/CLAUDE.md` 使用以下最小结构：

```markdown
# 项目工作流

## 项目概览

## 代码结构

## 构建与验证

## 开发流程

## 项目约束

## 项目 Skill
```

内容要求：

- 只写已确认的项目事实和负责人决定；
- “代码结构”只记录主要目录和顶层框架，不展开框架实现；
- “开发流程”明确区分需求理解、方案审核、实施授权和验证授权；
- “项目 Skill”规定独立、可复用的代码框架知识以后拆到 `.claude/skills/<name>/SKILL.md`；
- 新增或修改项目 Skill 前必须先提交名称、触发条件和范围给负责人审核；
- Agent 只读取当前任务匹配的 Skill，不一次加载全部项目知识。

### 6. 起草 Codex 入口

`AGENTS.md` 保持为薄适配层，使用下面的语义，不加入项目事实：

```markdown
# 项目 Agent 入口

- 开始任何任务前，完整读取并遵守 `.claude/CLAUDE.md`。
- `.claude` 是 Claude Code 与 Codex 共用的唯一项目知识源；不要在本文件复制项目规则。
- 如果 `.claude/skills` 存在，根据各 `SKILL.md` 的 `name` 和 `description` 判断当前任务是否匹配；只读取并遵守匹配的项目 Skill。
- 未经负责人审核，不得新增或修改项目工作流及项目 Skill。
```

### 7. 展示草稿并停止

在聊天中展示：

1. 将创建的两个准确路径；
2. `.claude/CLAUDE.md` 完整草稿；
3. `AGENTS.md` 完整草稿；
4. 明确未执行写入、构建或验证。

随后停止，等待负责人明确批准这两个草稿。设计讨论、继续分析或先前批准都不构成写入授权。

### 8. 获批后只写两个文件

写入前再次检查两个目标是否存在；出现冲突立即停止。

只创建必要的 `.claude` 目录以及两个获批文件。不要顺手创建 `.claude/skills`、说明文件、模板或其他目录。

发生部分写入或工具错误时立即停止，如实报告已经产生的文件；不要自动清理或修复。

### 9. 准确交付

报告实际创建的文件。不要自动运行构建、测试、格式验证、Git 提交或推送；这些动作需要负责人另行授权。

## 拆解模式

### 1. 读取共同工作流

- 完整读取 `<project>/.claude/CLAUDE.md`。
- 将根目录 `AGENTS.md` 仅视为 Codex 入口，不从中建立第二份项目知识。
- 如果 `.claude/skills` 已存在，只读取各 `SKILL.md` 的 `name` 和 `description` 以识别已有边界；不要一次加载所有正文。

### 2. 只读识别代码框架

只读取识别顶层框架所需的高价值信息：

- README、架构文档和项目清单；
- 主要代码目录、入口和模块边界；
- 框架之间明确存在的依赖关系；
- 当前任务需要且能够由文件证实的团队规则。

跳过依赖、缓存、构建产物和大型生成目录。不要运行构建、测试、格式化、安装或项目程序，也不要修改业务代码。

按职责和知识边界拆分，不按每个目录机械创建 Skill。候选框架必须满足：职责相对独立、来源路径明确、会在后续任务中重复使用，并且单独读取比加载整个项目更有效。

### 3. 展示拆分清单

为每个候选项目 Skill 展示：

- 名称；
- 触发条件；
- 覆盖范围；
- 来源路径。

同时列出暂不拆分的目录及原因。只展示候选清单，不创建目录或文件，然后停止等待负责人审核。

### 4. 逐个起草项目 Skill

候选清单获批后，只读取当前获批框架需要的来源文件，并逐个展示完整草稿：

- 主文件为 `.claude/skills/<name>/SKILL.md`；
- 只有内容确实需要时才提议 `examples.md` 或 `checklist.md`；
- 一个 Skill 只覆盖一个清晰框架，不复制 `.claude/CLAUDE.md` 的共同规则；
- `description` 写明真实任务触发条件，使 Claude Code 与 Codex 能按任务选择读取。

展示草稿后停止。候选清单批准、继续分析或草稿审核都不构成写入授权。

### 5. 获批后写入

负责人必须明确批准准确文件列表后才能写入。只创建获批的 `.claude/skills/<name>` 目录和文件，不顺手修改共同工作流、其他 Skill 或业务代码。

发生冲突、部分写入或工具错误时立即停止，如实报告已经产生的文件；不要自动清理或修复。

写入后只报告实际创建或修改的文件。不要自动运行构建、测试、格式验证、Git 提交或推送。

## 明确禁止

- 覆盖、合并、迁移或备份已有入口；
- 复制两份项目工作流或项目 Skill 正文；
- 根据项目类型注入预设 Unity、Unreal 或工具知识；
- 未经候选清单审核、草稿审核和写入授权自动创建业务 Skill；
- 启动子代理或扩大分析、实施、验证范围；
- 把“继续”“审核过设计”解释为写入或验证授权。
